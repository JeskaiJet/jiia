<Section title="为什么旅行预订需要一层关系？">
<WideImage src="/images/treeing/traditional.webp" alt="Treeing product overview" width={3840} height={2160} />

**TL;DR：传统平台只关注房源列表，忽略旅客与房东的长期信任关系。**

传统旅行预订平台通常从房源库存出发。旅客输入目的地、日期和人数，再通过价格、评分、位置和设施筛选结果。这套模式适合第一次探索，但不适合已经建立过信任的复购场景。

在真实旅行决策中，信任往往不是从零开始。旅客可能记得某次入住体验、某位沟通顺畅的房东，或希望再次预订同一位房东管理的其他房源。但在多数平台里，这层关系无法被保存成稳定入口。旅客需要重新搜索，房东也难以把满意客人沉淀成可持续经营的客群。

Treeing 的机会来自这里：把房东与回访旅客之间已有的信任关系结构化，让旅行预订从一次性搜索交易，转向围绕关系、复购和运营效率展开的产品系统。
</Section>

<Section title="把熟客关系变成三方都能受益的结构">
Treeing 的商业逻辑建立在旅客、房东和平台三方价值之上。

对旅客来说，Treeing 降低重复决策成本。用户不必每次旅行都重新筛选陌生房源，而是可以回到可信房东，查看新房源、可订时间和熟客权益。

对房东来说，Treeing 降低复购经营成本。很多房东已经有来自不同平台或线下渠道的老客人，但关系散落在短信、邮件、社交软件和平台后台里。Guest List 把这些熟客整理成可管理客群，并通过邀请、专属展示和运营工具持续维护。

对平台来说，Treeing 的价值不只来自房源库存，而来自关系网络。旅客与房东的关系越稳定，平台越有机会从一次性交易转向复购、留存和长期运营。

<Section title="从搜索压力到运营负担">
**TL;DR：旅客搜索复杂、房东维护成本高，是设计优化的核心问题。**

在梳理旅客与房东的使用场景时，我把问题分成两类：一类发生在预订前，另一类发生在长期运营中。

旅客侧的核心问题是搜索压力和信任迁移。旅行预订页面通常要求用户同时处理目的地、价格、日期、人数、地图、设施和评价。信息越多，决策不一定越轻松。到了移动端，桌面式筛选被压缩到小屏幕，用户更容易在多个条件之间反复确认。

房东侧的核心问题是关系管理和维护成本。多房源房东需要频繁处理价格、日历、可订状态和预订同步。如果 Treeing 只是增加一个新的后台，接入成本会很高。平台必须减少重复维护，而不是创造新的工作量。

这些观察让我把 Treeing 的核心问题定义为：如何同时降低旅客的信任决策成本，以及房东的复购运营成本？

<Section title="核心假设：让关系成为预订入口">
基于前期问题梳理，我把 Treeing 的产品假设总结为：

如果 Treeing 能把房东与熟客之间的信任关系变成可发现、可管理、可预订的产品结构，那么旅客可以更快完成可信预订，房东也能用更低成本维护复购关系。

这个假设进一步转化成三个设计原则：1.体验要围绕信任关系展开 2.房东不应为了接入 Treeing 放弃已有渠道。 3.运营工具要让状态和操作更清楚

<Section title="V1：先验证熟客关系是否能成为预订入口">

**TL;DR：V1 聚焦验证熟客关系是否能缩短预订路径，减少旅客搜索压力。**

Treeing 的第一版没有试图覆盖完整旅行预订平台，而是先验证一个更具体的问题：当旅客与房东之间已经存在信任关系时，平台能否把这层关系转化为更短、更自然的预订路径？

因此，V1 的设计优先级集中在三件事上。

- 旅客需要一个回到可信房东的入口。My Hosts 和 Host Page 让用户不必从通用搜索重新开始，而是围绕已经信任的人继续浏览。

- 房东需要一个管理熟客的基础模型。Guest List 把分散关系整理成平台内可维护客群，并通过 invitation 流程解释加入价值。

- 房东端必须足够轻量。Dashboard、Listing Editing 和 Calendar 相关工具支持日常运营，但不把 Treeing 变成另一个复杂后台。

</Section>

<Section title="降低旅客的搜索压力">
在旅客端，我重点处理搜索压力。传统搜索要求用户一开始就明确目的地、日期、预算、房型和偏好，但很多旅行决策并不是这样发生的。用户可能只是先看看合适选项，再逐渐收窄范围。

Spotlight 因此被设计成轻量推荐队列。它不要求用户先完成整套筛选条件，而是让用户通过浏览和滑动表达偏好。每一次交互既是探索，也是反馈。

移动端搜索采用分步流程，而不是把桌面搜索栏压缩到手机里。目的地、日期和人数被拆到独立页面或模态层中，用户一次只处理一个问题。小屏搜索因此更清晰，也减少误选和反复确认。

<Section title="把熟客关系产品化">
Treeing 的核心不是 Guest List 这个单一功能，而是围绕它建立一整层关系体验。

对房东来说，Guest List 是关系管理模型。它把分散在不同渠道里的常客整理成可管理客群，让房东持续维护关系，而不是每次重新获客。

对旅客来说，加入 Guest List 后，关系需要变得可见。My Hosts 提供长期入口，让用户快速回到可信房东。Host Page 则把房东从单个房源背后的运营者，提升为可以被关注、理解和再次访问的目的地。

Invitation 流程在这里很关键。用户不是被直接要求加入列表，而是先看到加入 Guest List 的价值：更容易回访可信房东，可能获得更好的价格或专属内容，也减少下一次预订的搜索成本。

<Section title="降低房东的运营成本">
如果 Treeing 只改善旅客端体验，却没有降低房东的维护成本，平台很难长期成立。房东是否愿意持续使用，取决于 Treeing 能否融入他们原有的运营工作流。

Host Dashboard 被设计成日常工作台，而不是单纯的数据展示页。关键经营信号、预订状态和日程信息在进入页面时立即可见。当房东需要进一步规划时，日历可以展开成更完整的运营视图。

Listing Editing 采用接近旅客视角的直接编辑方式。房东不需要在抽象后台表单中猜测最终展示效果，而是在接近最终页面的结构里修改内容。这减少了设置页面和展示结果之间的心理距离。

Batch Set 和 Calendar Connect 进一步解决多房源、多平台运营问题。Batch Set 把重复的价格和可订状态调整变成批量规则，Calendar Connect 通过外部平台同步降低接入成本。Treeing 的目标不是要求房东放弃已有渠道，而是成为更容易接入的复购关系层。

<Section title="从功能集合到关系型预订系统">
<WideImage src="/images/treeing/platform.webp" alt="Treeing web main page" width={2880} height={2048} />

**TL;DR：功能通过关系链连接，形成可复购、可持续运营的系统。**

Treeing 的最终设计不是一组分散功能，而是一套围绕关系运转的产品系统。

旅客端负责发现和回访。Spotlight 降低首次探索压力，Mobile Search 让移动端决策更清晰，My Hosts 和 Host Page 让可信房东成为可回访入口。

房东端负责关系管理和运营维护。Guest List 管理熟客关系，Dashboard 提供日常经营视图，Listing Editing 降低编辑理解成本，Batch Set 和 Calendar Connect 处理多房源、多平台维护负担。

这些功能连接起来后，Treeing 的核心逻辑才成立：旅客更容易回到可信房东，房东更容易维护熟客关系，平台也能从一次性交易转向长期复购。
</Section>

<Section title="Treeing 解决了什么问题">
Treeing 的设计收益可以从旅客、房东和平台三个层面理解。

对旅客来说，Treeing 减少每次旅行从零开始搜索的成本。通过 My Hosts、Host Page 和 Spotlight，用户可以在可信关系和轻量探索之间切换，而不是被迫一开始就完成复杂筛选。

对房东来说，Treeing 把熟客关系变成可管理资产。Guest List 帮助房东维护长期客群，Batch Set 和 Calendar Connect 降低多房源、多平台维护成本，Listing Editing 让房源更新更接近最终展示效果。

对平台来说，Treeing 的价值从房源库存扩展到关系网络。平台不只是促成一次预订，也帮助房东和旅客建立可以复访、复购、持续运营的连接。

<Section title="旅行平台不只是搜索">
**TL;DR：设计重点是关系如何成为预订入口，而非单页优化。**

Treeing 让我重新理解旅行预订产品的设计重点。这个项目一开始看起来像一个房源平台，但真正复杂的地方不是展示更多房源，而是判断平台应该围绕什么建立长期价值。

如果只从旅客端看，问题会被理解成搜索体验不够好。如果只从房东端看，问题又会变成后台工具不够高效。但 Treeing 的关键在于，这两个问题其实是同一个系统的两端。

旅客需要更可信的回访路径，房东需要更低成本的关系维护工具。只有这两端同时成立，熟客关系才可能成为平台价值。

最终，我把设计重点放在“关系如何成为预订入口”上，而不是单纯优化某一个页面。这也让我更明确地意识到：产品设计不只是把流程做顺，而是要找到业务模式、用户行为和操作效率之间可以闭环的位置。

</Section>
